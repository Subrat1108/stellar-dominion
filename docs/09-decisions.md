| 2026-06-14 | **Phase 3 is split 3A/3B** (Session 14) | 3A ships the minimal tunable core — **Temperature, Pressure, Hydrosphere** levers with direct lever→parameter effects + the Hydrosphere gate only. **Deferred to 3B:** Magnetosphere, Toxicity (Sabatier), Biosphere, and **all cross-lever feedback** (runaway greenhouse, pressure broadening, Urey drain, albedo trap). **No atmospheric stripping in 3A** — it arrives with the magnetosphere lever in 3B as a soft per-tick stripping drain on the volatile levers. Rationale: get the resource-sink + habitability-payoff loop working and balanced before layering feedback that is hard to tune in isolation. |
| 2026-06-14 | **Terraforming levers drive the body's real physical fields** (`surfaceTempK`, `atmosphere.pressurePa`, new `hydrosphere`), not a parallel gauge copy (Session 14) | These are exactly the inputs `computeHabitability` consumes, so recomputing habitability after each shift makes terraforming visibly raise the score, and the existing Phase 2C population model picks up the higher habitability as its growth factor with zero new wiring — one source of truth for body state. |
| 2026-06-14 | **Lever allocation is a per-lever 0–100% share, levers independent (not a shared 100% pool)** (Session 14) | Real resource scarcity (surplus power + stockpiles, via the same affordable-fraction cascade as production) is the natural limiter; an artificial shared budget adds UI friction without modelling anything physical. Power for terraforming is drawn from the colony's surplus generation that tick, giving propellant (pressure) and water (hydrosphere) their first real sinks. |
| 2026-06-14 | **Catalog bodies are deep-cloned into each world at setup** (Session 14) | The sim now mutates body fields (terraforming shifts temp/pressure/hydrosphere + rewrites habitability); inserting the shared module constants by reference leaked those mutations across worlds and into a new game / save. `structuredClone` per body keeps each world's state isolated and saves clean. |
| 2026-06-14 | **Legibility principle** added as Design Pillar 6 (Session 13) | Any system with dependencies must surface each element's inputs/prerequisites, its live status with a reason when blocked, and the current bottleneck — the player must always be able to answer "why isn't this working?" from the UI. Governs buildings (idle: no power / idle: insufficient water), population (popLimitingFactor), and future systems — including Phase 3 terraforming levers, which will show locked with the unmet prerequisite named (e.g. "requires: atmosphere > 0.1 atm"). |
| 2026-06-14 | **Known debt:** founding crew are counted both as ship crew and colony population (Session 12) | Simpler to seed colony.population = crew.members.length and keep named crew on the ship rather than splitting/transferring them; cosmetic for now since Phase 2C has no crew arc. Reconcile when the crew narrative lands (Phase 5–6). |
| 2026-06-14 | **Habitation Module power draw is meaningful:** unpowered modules apply a ×0.5 growth multiplier (Session 12) | Zero consequence for power loss makes the 3 pw draw feel decorative; halving growth makes power management matter for population, without blocking growth entirely (the dome is still standing). |
| 2026-06-14 | **Food critical requires net < 0** (same as oxygen/water) — a recovering stockpile below the threshold does not trigger starvation (Session 12) | A colony producing food faster than consuming it should never starve even if the absolute stockpile is temporarily low; requiring net < 0 makes the distinction legible and consistent with the oxygen/water model. |
| 2026-06-14 | **Population death rates proportional** to colony size (1.5 %/tick O₂, 1.0 % water, 0.4 % food) rather than flat per-tick losses (Session 12) | Flat losses hit small colonies disproportionately hard and make crisis timing inconsistent; proportional rates give a colony of any size ~15–30 s to 20% loss from an oxygen deficit, ~22 s from water, ~57 s from starvation, keeping the urgency consistent at every stage of growth. |
| 2026-06-14 | **Population is aggregate** — seeded from crew count at founding, grows/declines deterministically from that point via growth rate × habitability (Session 12) | Individual Pop tracking brings factional depth but scales poorly on the target hardware for multi-system play; aggregate is computationally cheap, sufficient for Phase 2C, and the ECS Colony component can add a factions map later without a structural rewrite (docs/09 Phase 5–6). |
| 2026-06-14 | **Light-lag** deferred to Phase 5+; when built, abstracted as **friction + forced delegation**, not literal input-lockout (Session 11 research) | Full input-lockout during distant fleet battles would be frustrating and hard to design around; abstracting it as growing unrest, tax compliance decay, and mandatory doctrine-delegation captures the strategic weight without locking the player out of their own game. Keeping it to Phase 5+ means we don't design around it before the single-system game is proven. See `docs/research/01`. |
| 2026-06-14 | **Terraforming** is an actively-managed, tiered, multi-stage loop — not a passive resource sink (Session 11 research) | A passive sink (pay credits, wait, habitability ticks up) is neither interesting nor scientifically faithful; the signature loop of the game is transformation, and that must require real player decision-making at each stage (mirrors, atmosphere, water, biosphere). Time is compressed for playability, but relative difficulty and ordering remain scientifically grounded (Venus >> Mars). See `docs/research/01` and `docs/04`. |
| 2026-06-14 | **Populations aggregate** (global stockpile + growth rate), not individual Pops; ECS left flexible for later factional sub-populations (Session 11 research) | Individual Pop tracking (Stellaris-style) brings rich factional depth but scales poorly on a MacBook Air across multi-system late-game; aggregates are computationally cheap, sufficient for Phase 2–3, and the ECS `Colony` component can be extended with a `factions` map later without a structural rewrite. |
| 2026-06-14 | **Player flight stays arcade** throughout; delta-v realism enters only as **abstracted automated-logistics costs** in Phase 4+ (Session 11 research) | Manual Tsiolkovsky calculation during piloting would make the flight model inaccessible and contradict the "grounded wonder, not punishment" pillar; the fun of approach is the feel of arriving at a world, not fuel budgeting. Delta-v as a logistics abstraction (transfer windows cost time + propellant drawn from stockpiles) in Phase 4 preserves the strategic depth without breaking the piloting experience. See `docs/research/01`. |
| 2026-06-14 | Colony **resource set is the full six** — Power, Water, Oxygen, Food, Metals, Propellant — with Propellant produced/stockpiled but having **no consumer until Phase 4** (Session 11) | The brief's Civilization-layer set is built whole rather than trimmed so the economy's shape is final and data-driven from the start; Propellant's only sink is in-system transfers (patched-conic/Hohmann), which belong to Phase 4 — until then it is an electrolysis byproduct that simply accumulates, so we don't build a propellant economy around it now. |
| 2026-06-14 | Colony economy runs on a **decoupled cadence** (`ECONOMY_TICK_INTERVAL = 60`), not the 60 Hz flight tick (Session 11) | Same decoupling idea as the orbital clock: the colony resolves once per ~60 flight ticks (≈1 Hz), gated deterministically on `world.tick % N`, so rates are authored per real-second and a bare starting reserve lasts minutes, not seconds. One tunable constant sizes the whole economy's pace; flight stays smooth at 60 Hz. |
| 2026-06-14 | Founding a colony **conserves ship supplies** — water + oxygen are offloaded from the life-support reserve, not created (Session 11) | Nothing from thin air: metals/food come from inventory, propellant from fuel, and the colony's seed water+oxygen are debited from `lifeSupport.current` (the reserve *is* stored air/water). Founding is rejected if the ship is short. Keeps the survival economy honest and makes founding a real commitment of consumables. |
| 2026-06-14 | Colony power-allocation priority puts **suppliers before consumers** (Water Extractor → Electrolysis → Hydroponics → Smelter) (Session 11) | Allocating (and drawing shared material) in this fixed order replenishes water before it is consumed, avoiding a water death-spiral under a power deficit; among the water consumers oxygen (electrolysis) still beats food (hydroponics), and metals (smelter) is shed first. The order also makes shortage cascades deterministic. |
| 2026-06-14 | **Multiplayer** remains a long-term vision, deferred indefinitely (post-MVP); no multiplayer code is built, but the headless, deterministic, serializable sim is preserved to keep a future **lockstep** model possible (Session 11) | Per `docs/02` parking lot and `CLAUDE.md` ("possible future multiplayer"): we don't build any netcode now, but every Phase-2 system stays a pure function of (seed, inputs/commands, tick) with serialisable state — so determinism, the command/event layer, and saves double as the foundation a lockstep multiplayer would need if we ever pursue it. |
| 2026-06-14 | Sim↔UI **command/event layer** built now at the start of Phase 2 (deferred since Session 4) (Session 10) | Discrete, state-mutating player actions (land, take off, found colony, set course) need validated, deterministic application inside the tick order — distinct from the per-tick continuous flight `Input`. Commands are plain serializable data drained at a fixed point each tick (`tick++` → drain → systems); results emit back as typed `GameEvent`s through `GameBus`. Keeps the sim headless/testable and gives Phase 2B's colony economy a clean entry point. |
| 2026-06-14 | Gravity is a **gameplay stat** (surface g → habitability/colony), not a flight force (Session 10) | Ship flight stays arcade (thrust + drag + scripted orbit) so piloting stays approachable on the target hardware; surface gravity is computed from mass/radius (G·M/r²) and consumed by habitability/colony logic, first surfaced in the landing view. Newtonian flight is an explicit optional post-MVP mode, not a Phase 2 dependency. |
| 2026-06-14 | Planet render radii scaled 6× (`PLANET_RADIUS_SCALE` 1→6, `PLANET_RADIUS_MIN` 0.7→4, `GAS_GIANT_SCALE` 0.26→1.5, `STAR_RENDER_RADIUS` 10→12) (Session 9) | At 1 u/R⊕ planets were invisible specks that never filled the view; at 6 u/R⊕ an Earth-sized world subtends ~66° at the 9 u autopilot park distance, making approach feel like reaching a real world. Orbit gaps remain healthy (tightest ≈22 u clearance between surfaces). |
| 2026-06-14 | Autopilot parks at `max(renderRadius×1.5, renderRadius+3)` from target centre (Session 9) | Hardcoded stop at dist<2 predated the 6× planet scale; new park point keeps the ship above the surface with the body filling the view — the pilot arrives facing a world, not a dot. |
| 2026-06-14 | Soft surface stop in ship-movement: clamp position + kill inward velocity when within `renderRadius+0.3` of any body (Session 9) | Prevents flying through planets; deterministic (same inputs = same outcome); handles the star via `STAR_RENDER_RADIUS` since the star has no Transform. |
| 2026-06-14 | Compass minimap: ship-centric, heading up, 4 zoom levels (20/80/300/800 u), scroll+buttons (Session 9) | World-fixed minimap became confusing once the system was large — heading up + ship centre makes bearing and zoom intuitive for navigation. Clipped blips pin to the edge so out-of-range bodies are still visible. Galaxy/interstellar zoom remains parked to Phase 5. |
| 2026-06-14 | Cockpit scanner: shows nearest body within 100 u; hidden in map view (Session 9) | Provides actionable info during approach without cluttering the flight view; `viewState` (plain mutable ref shared between renderer and React) drives visibility without extra prop threading. |
| 2026-06-13 | System spread to real-AU proportions: `AU_TO_SCENE` 12→200, `STAR_CLEARANCE` 8→4 (Session 8) | Planets were bunched and the throttle made them trivially close; real-AU spacing (Titan's Eye ~704 u, planet radii ~1 u) makes a planet read as a point that grows on approach. |
| 2026-06-13 | Ship `maxSpeed` 10→0.01, `BASE_ACCEL` 4→0.03, throttle range unchanged (1×–1000×) (Session 8) | Sizes the speed to the now-large system: 1000× crosses to Titan's Eye in ~1 min, 1× is fine docking; small base accel keeps an acceleration ramp instead of snapping to the cap. Accepted trade: 1× is precision-only, not a system stroll. |
| 2026-06-13 | Inverted yaw fixed in the sim layer (heading update + autopilot sign), not input mapping (Session 8) | `Input.yaw` already contracts +1 = right; ship-movement implemented it backwards (world +X renders screen-left), so the fix belongs where the contract is honoured and stays headlessly testable. |
| 2026-06-13 | Orbit model made moon-ready: `orbitalSystem` composes Kepler position with the parent's transform (Session 8) | A body can later orbit a planet by setting `Orbit.parent`; the transform-less star keeps children at the origin, so current behaviour and determinism are unchanged. Design-only, no moons built. |
| 2026-06-13 | System minimap is a fixed system-scale top-down radar (no zoom) (Session 8) | High-value, cheap navigation now; multi-scale moon/system/galaxy zoom is parked to Phase 5 to avoid building interstellar scale prematurely. |
| 2026-06-13 | Orbital time decoupled from flight time via `ORBITAL_TIME_RATE` (0.003→0.0015 in Session 8) | Planets advanced on real-time `world.time` and whipped around as you flew; a slow orbital clock keeps them nearly stationary during a flight while staying a deterministic function of tick. Halved in Session 8 because the larger orbital radii turn the same angular rate into more linear drift. |
| 2026-06-13 | All scene-scale constants centralized in `src/sim/presentation.ts`; render radii compressed (non-physical) | One tunable place for AU→scene distance, body render-radius, and ship size; physical radii span ~1:86 so a compressed mapping is needed for a legible ship≪planet≪star hierarchy. | 2026-06-13 | Flight simplified to six keys (W/S thrust, A/D yaw, ↑/↓ pitch); world-vertical removed | Space/Shift world-vertical was redundant with pitch-then-thrust and cluttered the scheme; climb/dive via pitch is enough and reads more like piloting. |
| 2026-06-13 | Speed lever is a **throttle** (scales ship accel/max-speed), not sim time compression | Playtesting showed time-compression made piloting feel disconnected; throttle gives direct control. | 2026-06-13 | Full 3D flight (yaw + pitch + world-vertical thrust); supersedes XZ-plane-only | Playtester needed to move in every direction; pinning to the orbital plane felt broken. Pitch clamped near ±90° to avoid gimbal flip. |
| 2026-06-13 | Floating origin via a single `worldRoot` group offset by -shipPos | Per-mesh offsetting left transform-less objects (the star) and static geometry (orbit rings, starfield) pinned, decohering the scene; one group moves everything together. |
| 2026-06-13 | Three camera views (cockpit / chase / map), C cycles, M toggles map | "Racing-style" inside + outside views per playtester; map kept for navigation. Cockpit hides the hull and looks down the nose. |
| 2026-06-13 | On-screen DebugPanel + throttled console log of ship telemetry | Lets bugs be diagnosed from a single screenshot/log during the flight-model bring-up. |
| 2026-06-13 | XZ-plane movement only (yaw, no pitch) for Phase 1B *(superseded same day)* | Matches the orbital plane; full 6-DOF adds complexity without payoff at this stage. |
| 2026-06-13 | Drag = 0.98/tick on ship velocity | Natural deceleration without a dedicated brake key; small non-Newtonian feel is an acceptable trade for playability. |
| 2026-06-13 | Floating origin is renderer-only; sim keeps absolute coordinates | Keeps serialization/saves simple; float-jitter only matters in the render layer. |
| 2026-06-13 | speedState is a plain mutable object, not React state | The frame loop mutates it synchronously; React only needs to read it on button click — React state would add unnecessary overhead. |
